# Spike: native apps (M0)

**Plan:** [native apps plan](../native-apps-plan.md), M0 and N34.
**Status:** Apple devices done; Android waiting for a device. Begun on 23 November 2026 in the iOS 27.2 simulator (iPhone 17) and an Android 17 (API 37, arm64) emulator, with Xcode 27.2, Tauri CLI 2.12.1 and NDK r30. From 24 to 25 November everything for Apple was run on physical devices: an iPhone 13 Pro Max (iOS 27.2.1), an iPad mini (6th generation, iPadOS 26) and an iPad Pro (iPadOS 26.6), with an Apple TV and a USB-C monitor. The Android column still comes from the emulator only; a Pixel 9 or 10 (not an "a" model, which may lack USB-C video) is the planned test phone. Windows discovery is next.
**Code:** the local `native-apps-spike` branch. It is throwaway.

## Findings for the real build

- **Gating.** Only window handling failed on mobile: `tauri-plugin-window-state` and `output.rs`. The spike gates them with `cfg(desktop)`, moves the updater and window-state crates to desktop-only dependencies, splits the capabilities by platform, and stubs the output commands.
- **The interface still calls the updater** on mobile ("updater.check not allowed"). The real build must not call it.
- **OpenSSL on Android.** `reqwest` with `native-tls` needs it. A vendored `openssl` on Android builds, but its build expects `aarch64-linux-android-ranlib` and `-ar`, which NDK r30 does not provide under those names. The spike uses links to `llvm-ranlib` and `llvm-ar`. Moving to `rustls` on Android is the alternative to weigh, and HTTPS to real servers from Android is not yet tested.
- **Android 17 local network permission is required.** With target SDK 37 and no grant, the app's connection to a private address **times out with no error that explains it**, while `adb shell` reaches the same address. The app must declare `ACCESS_LOCAL_NETWORK`, ask for it, and say so when it is refused.
- **Identifiers.** Tauri refuses an underscore in `identifier`. Setting `com.worship-q.app` gives `com.worship_q.app` on Android automatically, so one identifier serves both (N32).
- **Xcode from the command line.** The active developer directory is the Command Line Tools, and the Tauri CLI does not pass `DEVELOPER_DIR` on. The spike wraps `xcodebuild` and `xcrun`. `sudo xcode-select -s /Applications/Xcode.app` would remove the need.
- **Startup.** The white screen before the first draw needs a splash or a faster start. Measure it in a release build.
- **Keychain service name.** `keychain.rs` fixes `com.worship-q.desktop` as its service, which the mobile build should not reuse unexamined.
- **Associated Domains entitlement.** With `tauri-plugin-deep-link` configured for `app.worship-q.com`, Tauri CLI 2.12.1 did not write `com.apple.developer.associated-domains` into the entitlements file. The spike adds it by hand. The real build must check this, or links silently open Safari.
- **Running on an iPhone.** The phone needs Developer Mode and must be registered to the team. `xcodebuild -allowProvisioningUpdates -allowProvisioningDeviceRegistration` registers it and makes the profile; `tauri ios build` alone does not.
- **mDNS on iOS needs the system's Bonjour.** `mdns-sd` sends its own multicast packets, which iOS blocks unless Apple grants the restricted `com.apple.developer.networking.multicast` entitlement. Advertising reported success but nothing reached the network. The spike's `bonjour.rs` calls `DNSServiceRegister`, `DNSServiceBrowse`, `DNSServiceResolve` and `DNSServiceGetAddrInfo` from Rust (about 300 lines, no new crates beyond `libc`), which needs only `NSBonjourServices` and the local network permission, and it works. The real build should use it on iOS, and could on macOS, and keep `mdns-sd` elsewhere.
- **Choosing an address.** A discovered computer has several: Wi-Fi, IPv6 link-local and, with a cable attached, a `169.254` link to the Mac over USB. The spike's first pick was the USB link. The real build should try private IPv4 addresses first, then the others, and say which one worked. Look addresses up on any interface: limited to the interface the service was seen on, the lookup returned nothing.
- **Local network permission on iOS.** The prompt appears on the first LAN use. The app needs `NSLocalNetworkUsageDescription` and `NSBonjourServices` (`_worship-q._tcp`), which the spike adds through `src-tauri/Info.ios.plist`.
- **Logs from the device.** Stopping `devicectl device process launch --console` also ends the app.
- **Phones cannot serve in the background.** iOS suspends the app 10 to 17 seconds after it leaves the screen or the phone locks, and the LAN server stops answering. A phone can coordinate or relay only while Worship Q is on screen, and the interface should say so. Live audio listening needs the audio background mode, to test with the audio items.
- **The listening socket does not survive suspension.** After returning, connections were refused (the phone answered ping) until the app stopped and restarted its server. The spike does this on `visibilitychange`; the real build should do it from the app's lifecycle, and re-advertise.
- **Outgoing connections do not reconnect.** The phone's connection to the Mac sent nothing after the first suspension. The real build must notice and reconnect on return.
- **The desktop interface on an iPad mini, unchanged.** It is usable in both orientations: rail, run sheet, live preview and item sections all fit, and the sections flow side by side in landscape. Three things for the tablet work: the status bar and home indicator areas are **white strips** (the page should extend under them with `viewport-fit=cover` and pad by the safe-area insets, or the web view's background should match); the row arrows, item menus and edit buttons are smaller than the 44-point touch target; and nothing needs a hover.
- **External display on iOS 27 needs a scene accessory.** Declaring a `UIWindowSceneSessionRoleExternalDisplayNonInteractive` configuration in `UIApplicationSceneManifest` was not enough: with only that, AirPlay mirrored the iPad and `UIScreen.screens` stayed at 1. A view controller must call `registerSceneAccessory:` with `+[UISceneAccessory externalNonInteractiveSceneAccessoryWithConfiguration:]` (delegate class `TaoSceneDelegate`) and set the registration's `enabled`. Then iOS connects the scene, Tauri emits `RunEvent::SceneRequested`, and a `WebviewWindowBuilder` for the `output` label built in that handler joins the new scene, because tao attaches a new window to the scene that has none. The interface's existing `emitTo('output', …)` drives it unchanged. The spike does this from Rust with `objc2` (`spike_register_accessory` in `lib.rs`). Wired displays should behave the same; not yet tested.
- **tao bug: naming a second screen panics.** `MonitorHandle::name` compares against the main screen's `mirroredScreen`, which is nil, and `retained_new(nil)` panics ("messsaging retain to nil") inside a run-loop observer, aborting the app. It fires as soon as a second screen exists and the interface lists monitors. The spike patches `spike-vendor/tao`; report it upstream before the real build.
- **Panics on iOS.** Rust panic messages reach neither `devicectl --console` nor the crash report. The spike's panic hook appends them to the app's `tmp/spike-panic.txt`, copied off with `devicectl device copy from --domain-type appDataContainer`.
- **The display picker.** The interface still lists only the iPad ("not-on-mobile" from the stubbed `open_output`). The real build needs a mobile output module that reports the external scene as a display and lets the operator turn it on and off.
- **Websites on the external display.** Tauri's child webviews (`Window::add_child`) are desktop-only. The spike adds a native `WKWebView` (inline playback, no tap needed to start media) as a sibling over the output window's web view, from `output_website` through `with_webview`, and removes it when the website ends. The desktop's localhost YouTube page and its clock work unchanged on iOS. The website scale (plan N35) would apply to this view.
- **Safe area on external displays.** On iPadOS 26.6 the wired display's scene reported safe-area insets of 32 points at the top and 25 at the bottom, and the web view inset its content by them, leaving white bands. Setting the web view's `scrollView.contentInsetAdjustmentBehavior` to never and its background to black removed them (`spike_no_insets`). The iPad's own window has 32 and 20, which are the white strips in the operator interface; the interface should draw under them with `viewport-fit=cover` and pad by `env(safe-area-inset-*)`.
- **iOS versions.** iPadOS 26 connects the external display scene from `UIApplicationSceneManifest` alone; iOS 27 also needs the scene accessory. One build does both: the accessory is registered only where `UISceneAccessory` exists.
- **YouTube on the wired display was not reliable on the first try.** After a slide it showed black, and after a website the website stayed, while the local video page answered `200`. The next build, which changed only the insets and added diagnostics, played it. The cause is unknown; the real build needs a navigation delegate on the website view that reports failed loads.
- **Recording a broadcast that went to the background.** On iOS the capture track is muted, not ended, while the app is hidden, and `MediaRecorder` simply records nothing until it is unmuted, so the gap disappears from the file and the recording no longer lines up with the clock or the presentation log (service records R5, R16). The real build must treat a mute as the end of a recording (R5's "muted and taken again"), or stop and start the recorder on visibility changes, so an interruption leaves two whole recordings.
- **Choosing the input.** iOS names USB inputs as their product names, and a hub's own audio device shows up beside the real one ("USB Advanced Audio Device", silent here). The broadcast settings must let the operator pick the input and show its level, as the desktop's do; never pick the first USB input.
- **Microphone text.** The desktop's `NSMicrophoneUsageDescription` speaks of listing devices for video sound; the mobile app needs its own, about broadcasting (the spike's `Info.ios.plist`).
- **A listener stays alive in the background.** While audio plays, iOS does not suspend the app: its timers kept running (every 3 seconds instead of 2) and its connection to the Mac stayed up. This is what the audio background mode is for, and App Review accepts it for an app that plays audio the user started. The app must not lean on it for anything else: serving the LAN from a locked phone that is not playing is still not possible (background row above).
- **Where waiting chunks live on a phone (N28).** IndexedDB in the web view survives the app being killed, which is what service records R7 needs. Two doubts remain: `persist()` is refused, so the system may clear the data under storage pressure, and `estimate()` does not report Blob storage, so the 500 MB limit cannot be enforced from it. Either keep IndexedDB and count bytes in the app, accepting that iOS may clear it on a nearly full phone, or move the queue to files through the Rust core, which iOS clears only when the app is deleted. The second is safer for recordings.
  - **Low storage, iPad mini (iPadOS 26, 256 GB).** A 68-second clip left 14 chunks (551 KB). A filler file then took free space from 122 GB to 299 MB; on the way, iOS reclaimed about 4 GB of other data, and within a minute it brought free space back to about 3.4 GB. After a relaunch all 14 chunks were still there, with no bad reads. The app's own caches were untouched. WebKit kept reporting the same quota (10.3 GB) throughout, so the quota tells the app nothing about free space; the app must read free space itself (statvfs works). A second run kept writing while iOS freed space: the filler reached 150 GB, about 21 GB more than was free at the start, and iOS held free space between about 0.9 and 3 GB by clearing other data as fast as the app wrote. A 2-minute clip recorded in that state saved all 27 chunks with no write errors, and after a relaunch all 41 chunks from both clips read back intact. This shows iOS does not clear the app's IndexedDB on a short, sharp squeeze, and that iOS keeps a floor of free space by purging other data rather than refusing the app's writes. It does not show what happens to a phone that stays nearly full for days, so the case for moving the queue to files stands.
- **Fonts on iOS need a platform call.** `fontdb::load_system_fonts` finds nothing on iOS, where system fonts are not in readable folders. The font picker would be empty and the missing-character warning silent. `UIFont.familyNames` gives the families (as the spike's `spike_uifont_families` does), and glyph coverage can come from `CTFontCreateWithName` with `CTFontGetGlyphsForCharacters`. Fonts an operator installs through a configuration profile or an app appear in the same list.
- **Presenter Mode touches.** The native website view must have user interaction off, or a tap pauses a YouTube video (the app's clock restarts it) and swipes over a website never reach the slideshow. Swipes must send the clicker keys (Page Down, Page Up): the arrow keys mean next and previous item, or next slide only in one layout.
- **Closing windows on iOS.** `WebviewWindow::destroy` leaves the label registered, so a second `WebviewWindowBuilder` with it fails. Hide and show, or find out why tao sends no destroyed event.
- **YouTube Mix links.** The Share button on a Mix gives `youtube.com/playlist?list=RD<video id>&playnext=1`, which `youtubeVideo` does not read as a video, so the item shows YouTube's own site: on a phone, the mobile site, which starts muted and could only be unmuted by a tap. A single video's link played through the app's page with sound on the iPhone. Fixed on main in `769c3b2`: a Mix's list id is `RD` and its seed video, which the parser now takes; with the fix, the shared Mix played through the app's page with sound on the iPhone. Other playlists still show as web pages, as they cannot follow the one-video clock.
- **Presenter Mode controls over a website.** The controls are drawn in the slideshow page, under the website view, so the spike fades the website to a quarter while they show (`spike_website_dim`); a second tap brings it back. The real build should draw them above the website view.
