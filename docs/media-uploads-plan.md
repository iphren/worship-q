# Worship Q — Media Uploads Plan

**Drafted:** 1 November 2026; requirements added 7 November 2026 (U12–U23)  
**Status:** Draft for review; tasks in the [task breakdown](media-uploads-task-breakdown.md). U11 is implemented (admin Storage page). Nothing else here is implemented yet.  
**Source:** [Requirements and Architecture](worship-q-requirements-and-architecture.md) (spec §§ on backgrounds and media), the "Unscheduled" items in the [Phase 2 Plan](phase-2-plan.md) (live audio broadcast), the project owner's requests of 7 November 2026 (Media tab, upload progress, image size, Download original), and the code at version 2.0.0.

## 1. Where the implementation stands

- The server accepts any single file up to 2 GB (`MAX_FILE_BYTES` in `apps/server/src/app.ts`), whatever its type. `/api/v1/info` reports only whether slide decks can be converted (`decks`), not any limits.
- Slide decks are converted on the server into slide images, small copies and text (`apps/server/src/decks/convert.ts`, needing LibreOffice and Ghostscript). The uploaded original is kept next to the images as `deck-<id>-original.<ext>` (part of U4), but nothing uses it yet and no route serves it. Decks imported before version 0.5.2 have no original.
- The import runs in one request: the native core streams the file to `POST /api/v1/decks` (`import_deck` in `src-tauri/src/cloud.rs`) and gets the deck back when conversion is done. The interface only knows "converting" and then "fetching *n* of *m*" images. It cannot tell how much of the file has been sent.
- A run sheet item can only refer to a song. A slide deck or a website is a song with a `deck` or `website` field. Images reach the screen only through imported slide decks or backgrounds.
- Videos reach the screen only as song backgrounds, and background videos are always muted.
- The library tab lists songs in three tabs: **Songs**, **Slides** and **Web** (`apps/desktop/src/pages/SongsPage.tsx`). Slides are imported from the Slides tab only. A run sheet gets items only from its song search.
- The admin web app's Storage page (U11) counts deck images, deck originals, background images and videos, backups and the database. It reports the space pruning (U5) would free, but pruning itself is not implemented.

## 2. Features

- **Media tab:** the library's **Slides** tab becomes **Media** and holds slide decks, PDFs, images and videos together. One **Add media…** button takes any of them (U12).
- **Image and video run sheet items:** upload an image or video and add it to a run sheet as an item of its own, not only as a song background. A video item's sound plays only from the slideshow (see audio device settings).
- **Images fit the screen:** an uploaded image is reduced on the server so it is no wider than 1920 pixels and no taller than 1080. A smaller image is never enlarged (U13).
- **Upload progress:** whenever media is added (in the library, in the calendar's run sheet editor, or in Live's run sheet), a progress bar shows how much of the file has been sent. Slide decks, PDFs and images then show an animated processing bar while the server works on them. Videos need no processing and are ready as soon as they are sent. In a run sheet the bars are on the item itself; in the library they are under the search box (U15, U16).
- **Download original:** a media item has a **Download original** button that saves the file as it was uploaded (U18).
- **Audio device settings:** choose the audio input device (the source for live audio broadcast) and the audio output device. When the slideshow is open and a video item is playing, its sound plays through the chosen output device. Previews never play sound, and background videos stay muted.
- **Video playback controls:** while a video item is live, the main window and the phone remote show a video control bar. A video item starts paused, unless **Autoplay** is turned on for it in its editor, in which case it starts playing as soon as it is presented (U23). Throughout a live session, each video item remembers where it was left: switching back to it from another item or slide continues from that position instead of the beginning (U22). While it is live, the keyboard shortcuts change: Space plays or pauses (instead of unblank-or-next), Left and Right jump backwards and forwards through the video (instead of previous and next item), and Up and Down move to the previous and next run sheet item (instead of previous and next slide).
- **Drag and drop files:** drag a compatible file (a slide deck, PDF, image or video) onto the run sheet column, in the editor or in Live, and drop it at a chosen position. The app uploads it, waits for processing (such as slide conversion on the server), and adds the item at that position. On the library tab, a dropped file is added to the library only, not to the current run sheet.

## 3. Decisions

| # | Topic | Decision |
| --- | --- | --- |
| U1 | Size limits per type | Images **25 MB**, slide decks and PDFs **200 MB**, videos **200 MB** by default. Each limit can be changed by the server administrator (for example `WORSHIP_Q_MAX_VIDEO_MB`). |
| U2 | Where limits are checked | The server reports its limits in `/api/v1/info`. The desktop app checks a file's size before sending it, so a file that is too big fails at once with a clear message. The server still enforces the limit while receiving. |
| U3 | Reverse proxy | The deployment guide states that the proxy's request body limit (nginx `client_max_body_size`, default 1 MB) must be at least the largest upload limit; otherwise uploads fail with a 413 error. |
| U4 | Slide deck originals | The original file is kept on the server next to its converted images. Presenting uses only the images. The original allows **Reconvert** (after installing a missing font, or when the output size or the converter changes) and **Download original**. |
| U5 | Pruning originals | Optional, if disk becomes a concern: originals of decks not used in a run sheet for 6 months are removed, and their images are kept. Reconvert and Download original are then unavailable for that deck. |
| U6 | Videos are uploaded like everything else | Every video is uploaded to the server. There is no local-only video: a file over the limit is refused and not added to the library. |
| U7 | Message when too big | "This video is 640 MB; this server accepts up to 200 MB. Export a smaller version and try again." The limit shown is the server's current setting. |
| U8 | Caching videos for the run sheet | A computer downloads and keeps a copy of every video in today's and upcoming run sheets, so playback never streams from the server during a service. The download starts as soon as the video is in such a run sheet, and items show their download progress until the copy is ready. Past run sheets do not keep copies. |
| U9 | Removing cached videos | A copy is deleted once no current or upcoming run sheet uses the video. If the video is needed again, it is downloaded again. |
| U10 | No server-side video processing | The server stores videos as uploaded and never shrinks or converts them. A video over the limit must be exported smaller before uploading (U7). |
| U11 | Storage monitor in the admin web app | The admin web app (phase 3) shows how much space the server uses, broken down by type of resource: slide deck images, slide deck originals, images, videos, backgrounds, desktop backups, and the database. Each type shows its total size and file count, overall and per workspace, next to the free space left on the data volume. Slide deck originals show how much pruning (U5) would free. The page is for viewing only; removing content still happens through the normal delete actions. **Implemented**; image and video items are added to it by U13 and U14. |
| U12 | Media tab | The library's **Slides** tab is renamed **Media**. It lists slide decks, PDFs, images and videos, each with a small badge for its kind. Its button is **Add media…**, and its file dialog accepts every supported format. The Church Library type keeps its stored name `slides` (in `LIBRARY_TYPES`, workspace settings and the admin app), so servers and existing workspaces need no migration; only its label becomes **Media**, in the desktop app and in the admin app. **Agreed.** |
| U13 | Images are one-page decks | The server turns an uploaded image into a deck with one page. The image is reduced to fit within **1920 × 1080** (never enlarged, turned upright from its camera orientation, transparency filled with black) and saved as JPEG, with a 320 × 240 small copy for phones, like a slide. The original is kept as `deck-<id>-original.<ext>`, as for slide decks (U4). Presenting, phone thumbnails, file synchronization, the Storage page and pruning (U5) then work for images unchanged. The deck records its kind (`kind: 'image'`, otherwise slides) for the badge and the Storage page. Accepted: JPEG, PNG, WebP and GIF (first frame); HEIC only if the M0 spike shows the server can read it, otherwise refused with "Export the photo as JPEG and try again." Resizing uses the `sharp` library on the server, so images work even where LibreOffice is not installed. **Proposed.** |
| U14 | Videos are songs with a video | A video item is a song with a `video` field, as decks and websites are: the stored file's name (`video-<id>.<ext>`), the uploaded file's name, its pixel size, duration and byte size, and whether it plays on entry (`autoplay`, U23). The server stores the file as uploaded (U10). Accepted: MP4 and M4V (H.264 or HEVC), MOV and WebM, subject to the M0 spike showing both platforms play them. The computer that uploads a video keeps its own copy, so it never downloads it back. **Proposed.** |
| U15 | Two stages of progress | **Uploading:** a bar that fills with the share of the file sent, with the percentage, reported by the native core as it streams the file. **Processing:** for slide decks, PDFs and images only, an animated striped bar (diagonal stripes that move, like `// // // //`) with "Processing on the church server…". It covers the conversion and fetching the converted images back to this computer. Videos skip it and are ready once sent. A failure replaces the bar with the reason, **Try again** and **Dismiss**. An upload can be cancelled while it is being sent, but not while it is processing. **Agreed.** |
| U16 | Where progress shows | **Run sheet** (the calendar's editor and Live): on the item itself. The item appears at once, at the position where it will land, with its file name and the bar. It turns into the ordinary item when the media is ready. Until then it exists only on this computer: other computers and phones see the item only once it is ready. **Library:** under the search box, one row per upload with the file name and the bar; several uploads stack. When an upload in the library is ready, its item opens in the editor. Uploads carry on when the operator moves to another tab or page; only quitting the app stops them. **Agreed.** |
| U17 | Adding media to a run sheet | By dropping files on the run sheet (Features), and with an **Add media…** button next to the song search in both run sheet editors, which adds to the end. Each file becomes its own media item in the library as well. A file dropped on Live's run sheet from a follower is placed using the existing `addItem.afterItemId` of the coordinator's edit commands. **Proposed.** |
| U18 | Download original | A **Download original** button in the media item's editor saves the uploaded file under its original name, through a save dialog. Decks, PDFs and images: the kept original from the server (a new device route), with download progress. Videos: this computer's copy when it has one, otherwise the server's. Decks imported before originals were kept, or whose original was pruned (U5), show the button disabled with "The original file was not kept for this item." It needs the church server, as importing does. **Agreed.** |
| U19 | What the server offers | `/api/v1/info` gains `media`: whether images and videos are accepted, and the limits of U1. Against a server without it, the Media tab still imports slide decks and PDFs, and says "Images and videos need an update of your church's server." **Proposed.** |
| U20 | Older desktops | A desktop from before this work sees an image item as a one-page deck and presents it normally. It sees a video item as an item with a title and nothing to show. To keep such a desktop from losing the video when it edits the item's title, the server keeps a song's `video` when an update from a device older than protocol version 5 leaves it out. Churches are asked to update every desktop before using video items. **Proposed.** |
| U21 | Protocol version 5 | Needed for video playback (play, pause and jump commands, and the playing position in the live state) and for U20. The minimum stays 2. A version 5 desktop against a version 4 server uploads and presents images and decks, and offers no video items. **Proposed.** |
| U22 | Remembering the play position | The live state keeps the last position of each video item, keyed by run sheet item, like `lastShown` does for slides. The position is saved whenever the video stops being on screen: another item or slide is presented, the screen is cleared, or the presentation ends. Presenting the video item again continues from that position, whichever way it is reached (click, Next, Previous, phone). A video that was left at its end starts again from the beginning. Presenting the video item that is already live changes nothing. Blanking pauses a playing video where it is, and unblanking resumes it, unless the operator played or paused it while blank; the operator's own pause is never undone by unblanking. The memory lasts as long as the live session: **End** or **Go live** on another run sheet forgets it, and removing the item from the run sheet forgets its position. The same video used twice in one run sheet has a position for each item. **Agreed.** |
| U23 | Autoplay | Each video has an **Autoplay** switch in its editor, off by default. It is part of the video's record, so it is the same on every run sheet that uses the video and on every computer. On entry, a video with Autoplay plays from its remembered position (U22). One without Autoplay waits, paused there, until the operator plays it. If the screen is blank when an Autoplay video is presented, it waits paused and starts playing when the screen is unblanked, unless the operator has played or paused it in between: the same rule as a video paused by blanking (U22). Changing Autoplay while the video is live takes effect the next time it is presented. Videos saved before the switch existed have it off. **Proposed** (the blank-screen rule). |

## 4. Open questions

- **Choosing the audio output device on macOS.** The app's webview on Windows (WebView2) can send a video's sound to a chosen device (`setSinkId`). The macOS webview (WKWebView) may not support it. The M0 spike settles whether macOS gets the setting or uses the system's output.
- **Device names need microphone permission.** Webviews list audio devices without their names until the app has been allowed to use the microphone. The input device setting asks for that permission anyway, so the output setting may need to ask for it too. To check in M0.
- **Dropping on the Media tab while another library tab is open.** Proposed: a dropped media file goes to the Media tab, which opens to show the progress.
